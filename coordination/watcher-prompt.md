# Slack Approval Gate Watcher

In-session polling instructions — see docs/superpowers/specs/2026-09-25-slack-approval-gate-design.md for the full design. Not a separate scheduled agent: this runs inside the same interactive Claude Code session that created the gate, only while that session remains active. There is no cloud/scheduled-agent watcher — cloud agents can't see local, uncommitted gate state, and a real gate creator's session can just poll directly instead.

After creating a gate and telling the user it's posted, if you want to actively watch for a Slack reply rather than only waiting for the user's next chat message, poll `#network-monitor` every 60 seconds (tracking the last-read message, not the last-sent one, per this repo's existing Slack-monitoring convention) until the gate is resolved or the session ends:

1. Run `coordination/scripts/gate-status.sh <linear_id> <slug>` for the gate you created. If it is `blocked`, stop. If it is `approved delegated=true`, stop because delegation is complete. If it is `approved delegated=false delegation_claimed=false`, the task already has approval: claim it with `coordination/scripts/claim-gate-delegation.sh`, then route and dispatch it as below without asking for approval again. If it is `approved delegated=false delegation_claimed=true`, do not dispatch; ask the human to confirm no delegation is active, then reset the claim with `coordination/scripts/reset-gate-delegation-claim.sh <linear_id> <slug> --confirm-no-active-delegation`, claim again, and continue. Only `awaiting-approval` proceeds to Slack polling.
2. Read the `#network-monitor` Slack channel for messages or thread replies mentioning `<linear_id>-<slug>` posted after the gate's `posted_at`.
3. If there's no qualifying reply yet, wait 60 seconds and repeat from step 1.
4. If there's a qualifying reply, use your own judgment to classify it:
   - **Clear approval** ("approved", "go ahead", "yes", "lgtm", etc.): run `gate-status.sh` first. If it shows `awaiting-approval`, run `approve-gate.sh`. Then run `claim-gate-delegation.sh`; dispatch only if that claim succeeds. Decide routing via `coordination/router-checklist.md`, carry it out (spawn the right in-session subagent or run `new-task.sh` for Codex work), then run `mark-gate-delegated.sh`. If approval was already recorded, resume only when `delegated=false delegation_claimed=false`; a completed delegation needs no action, and an incomplete existing claim requires the explicit human-confirmed recovery described in step 1.
   - **Clear rejection**: run `coordination/scripts/block-gate.sh <linear_id> <slug> "<why, from the reply>"`, then reply in the same Slack thread acknowledging it's blocked. Do not delegate. Do not retry.
   - **Unclear / a question, not a decision**: reply in the Slack thread asking for a clear approve/reject. Keep polling — the gate stays `awaiting-approval`.
5. If the session ends before the gate is resolved, polling stops. A future session can continue an `awaiting-approval` gate after a new approval, or resume an `approved` gate that has no delegation claim. An incomplete claim is never retried automatically; the human must confirm no dispatch is active before resetting it.
