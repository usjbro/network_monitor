# Security

## Current posture (loopback by default, opt-in mTLS-gated LAN access)

This tool captures and displays real, sensitive data about your own device: every process's network connections, remote IPs, DNS queries, TLS SNI hostnames, and raw packet bytes. Treat it accordingly.

**Where it stands today:**

- **The two core processes still bind to `127.0.0.1` only.** The capture agent listens on `127.0.0.1:9990`; `npm run dev`/`npm run start` explicitly pass `-H 127.0.0.1`. Neither is directly reachable from your LAN.
- **Neither of those two processes authenticates anything, by itself.** Whatever *can* reach those ports reads the full capture feed and can pause it via `/api/control`. That remains acceptable only because they are loopback-only — all access control lives in the Caddy layer in front of them, described next.
- **LAN access, when you opt into it, goes through mutual TLS.** `deploy/` provides a Caddy reverse proxy configured with `client_auth { mode require_and_verify }` against a local mkcert-issued CA: a client with no certificate, or with a certificate not signed by that CA, never reaches the app. Enforcement is not assumed — `deploy/test-mtls-rejection.sh` proves it, with three checks (missing cert rejected, valid cert accepted, *untrusted self-signed cert rejected*), and that third check is what distinguishes a correct `require_and_verify` from a `mode require` misconfiguration that would accept any self-signed cert. See `deploy/README.md`.
- **That LAN exposure is off until you turn it on, and it takes two deliberate edits.** `deploy/Caddyfile` ships with `bind 127.0.0.1` and a `localhost:8443` site address. Step 5 of `deploy/README.md` is the manual switch to `:443` on all interfaces; nothing in this repo does it for you. Note that the *site address alone does not control the interface* — Caddy binds the wildcard address unless a `bind` directive says otherwise, so `bind` is what actually keeps the default loopback-only. Verify with `lsof -nP -iTCP:8443 -sTCP:LISTEN`.
- **The native macOS viewer (`macos-app/`) is a deliberately minimal client.** A `WKWebView` locked by `NavigationLockDelegate` to exactly one origin — scheme *and* host *and* port must all match, so neither a plaintext `http://` downgrade nor a different port on the same host is reachable — with `window.open`/new-window requests refused outright. Its mTLS client certificate is backed by a non-extractable P-256 Secure Enclave key (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, no iCloud sync, biometric confirmation per signing use); the private key material never leaves the Secure Enclave.
- **The served page sets a nonce-based Content-Security-Policy** (`middleware.ts`, CSP string built by `lib/csp.ts`), and HTML-escaping of network-sourced strings is audited and regression-tested (`lib/__tests__/no-dangerous-html.test.ts`) so a crafted DNS query name, HTTP path, or process name can't inject markup. One narrow, fail-closed carve-out: `script-src` adds `'unsafe-eval'` only when *both* `NODE_ENV === 'development'` (allow-listed, not `!== 'production'` deny-listed, so any unexpected/stray env value stays strict) *and* the request carries no `x-mtls-verified` header (direct loopback access, not proxied through Caddy) — needed because Next.js dev mode's Fast Refresh/HMR client requires `eval()` to apply hot updates, and `deploy/README.md`'s "Running" section documents `npm run dev` as an accepted alternative to `npm run start` for the real LAN-facing, mTLS-authenticated session, so `NODE_ENV` alone can't tell loopback dev browsing apart from real proxied traffic hitting the same dev server. Same header-based gate `lib/decrypted-payload-gate.ts` already uses for `decrypted_payload` events. See `lib/__tests__/csp.test.ts`.
- **The capture agent runs unprivileged at runtime**, via macOS's `access_bpf` group rather than `sudo`/root. If the agent process is ever compromised (e.g. a bug in its packet parser), the blast radius is "your BPF-group-scoped user," not "root."
- **The packet parser is hardened against its highest-risk input**: it parses untrusted, attacker-reachable network bytes (any device that can send you a packet can influence what the agent parses), so every parsing function returns `Option`/`Result` rather than panicking, and `capture-agent/src/parse.rs`'s entry point is fuzzed via `cargo-fuzz`.
- **No secrets or credentials are handled anywhere in this pipeline.**
- **Ownership enrichment (WHOIS/RDAP, epic #23) was this app's first outbound network dependency, and it ships default-off.** Turning it on (`enrich on` in the command bar) is a runtime-only opt-in — never persisted, so it's off again after every relay restart — that queries public RIR/registrar RDAP servers (ARIN, RIPE, APNIC, LACNIC, AFRINIC, plus a handful of registrar RDAP hosts and a deliberately tiny, <=5-entry legacy WHOIS-fallback allowlist for domains) and, for the extended tier's registrant lookups, resolves a reverse-DNS PTR hostname via the relay's own configured DNS resolver. Every one of those queries is cache-first (14-day TTL, 1-hour negative-cache), rate-limited to one in-flight request with 3-10s jitter between them, and SSRF-hardened (`redirect: 'manual'`, response-controlled host allowlists that reject anything not on the reviewed list — including a redirect or referral pointing back at loopback/internal addresses). Results and the outbound query audit log live under `.data/enrichment/` (`0600` file permissions, 30-day query-log retention); `enrich clear` wipes both. See `docs/superpowers/specs/2026-08-28-ownership-enrichment-design.md` for the full security model and its threat table.
- **GeoIP lookups (epic #24) are a second, later outbound dependency, following the same opt-in shape.** Per-hop geoIP resolution during a traceroute is off unless requested and goes through `lib/geoip.ts`; see `docs/geoip-protocol.md` for the request/response contract and allowlisting. The ICMP traceroute probes themselves (`capture-agent/src/traceroute.rs`) are on-demand only — the agent never starts one on its own — and are bounded agent-side regardless of what the relay sends: a 30-hop ceiling, per-hop retry/timeout, and a 45s total-trace timeout.
- **TLS content visibility (epic #25) decrypts traffic for one process at a time, opted in explicitly, never as a blanket proxy.** Decryption only happens for a process launched through `bin/osi-inspect.js`, which points `SSLKEYLOGFILE` at a fresh, ephemeral, `0600` key-log file and registers that one PID as decrypt-eligible with the agent over the existing control channel (unregistering on exit). There is no CA installed, no certificate forged, and no traffic redirected — the agent decrypts a copy of the traffic it already passively observes, using key material that process's own TLS library wrote out at its own request. Decrypted content lives only in a capped, `mlock`'d, zeroed-on-evict ring buffer (`capture-agent/src/ring_buffer.rs`) — it is never written to disk — and passes through a sensitive-header redaction pass (`src/redact.rs`) before reaching the wire. On the relay side, `lib/decrypted-payload-gate.ts` additionally restricts rendering the decrypted-content event to loopback or mTLS-authenticated transport, so it can't leak to an unauthenticated LAN client even if enabled. See `docs/superpowers/specs/2026-08-29-tls-interception-design.md` for the full threat model, including why this design was chosen over a MITM proxy.

## Residual risks in the LAN-access design (epic #22, now landed)

The mTLS work is implemented and verified, but it is a *local-CA, single-user* design with real, deliberate limitations. Know these before you turn on LAN access:

- **The mkcert CA private key sits unencrypted on disk at `~/Library/Application Support/mkcert/rootCA-key.pem`.** It has no passphrase; the only thing protecting it is Unix file permissions (mode `0400`, owner-only). Any process running as your user can read it — and anything that reads it can mint a client certificate that Caddy will happily accept. Worse, because `mkcert -install` adds that CA to your system and browser trust stores, that same key can also mint a *server* certificate for any hostname on the internet and MITM your own browsing. This is the single highest-value secret this design creates, and it is not hardware-protected the way the client key is.
- **Client certificates are long-lived and there is no revocation mechanism.** Revocation via OCSP/CRL is intentionally out of scope (see the plan's Global Constraints); the stated substitute is short-lived, periodically-reissued certs. In practice `setup-ca.sh` takes mkcert's default validity, which is about **two years and three months** (verified: a cert issued 2026-08-28 expires 2028-11-28) — not short-lived. If a device is lost or a client key leaks, your only real remedies are to reissue the entire CA and redistribute to every device, or to stop trusting that CA. Consider narrowing validity if this matters to you.
- **`:443` binds every interface.** Once you make the `deploy/README.md` step 5 change, the capture feed's front door is reachable from anything that can route to your Mac, and mTLS is the *only* thing standing in front of it. That is the intent — but it means a Caddy misconfiguration is now directly exposed rather than merely loopback-visible, which is exactly why `deploy/test-mtls-rejection.sh` exists and should be re-run after any change to `deploy/Caddyfile`.
- **The native app's certificate provisioning was confirmed working end-to-end on real Secure Enclave hardware — the app never touches the CA private key.** App Sandbox blocks that outright (confirmed: `errSecMissingEntitlement`, `OSStatus -34018`, without granting a broad file-read entitlement this design deliberately avoids). Instead, `deploy/sign-native-app-csr.sh` — a plain, unsandboxed script run once from Terminal — reads the CSR the app writes to its own sandbox container and writes the signed certificate back there; the app polls for it and imports it automatically. See `macos-app/README.md` ("Provisioning the client certificate") for the full flow, and `macos-app/OSINetStrikerViewer/ClientCertStore.swift` for the implementation. This does mean `deploy/sign-native-app-csr.sh` has the same access to the CA private key `deploy/setup-ca.sh` always has — nothing new is exposed, it's just a second script that reads the same file.

## What's explicitly NOT done yet

- **The internal hops are still plaintext**, by design — agent↔relay is plaintext TCP on `127.0.0.1:9990`, relay↔Caddy is plaintext HTTP/SSE on `127.0.0.1:3000`. Fine on loopback (that traffic never leaves your machine's kernel). TLS exists only on the outermost hop, Caddy↔client.
- **No application-layer authentication** on the SSE stream or the control endpoint. Identity is established once, at the TLS layer, by Caddy. The app itself still has no concept of a user, a session, or a permission, and the relay cannot tell one authenticated client from another — every client that gets past mTLS has identical, full access. Ownership enrichment's opt-in (above) inherits this same gap: it's a **relay-wide toggle, not per-viewer** — one browser session typing `enrich on` enables outbound queries, and reveals results, for every session currently attached to the relay. Fine for today's single-operator, loopback-only relay; once LAN access (epic #22, above) puts multiple trusted devices on the same relay, a relay-wide enrichment toggle stops matching a reasonable consent model. Named, tracked limitation for sub-project 1b, not a silently-dropped concern — see the design spec's "Explicitly out of scope" section. TLS content visibility (epic #25, above) sidesteps this specific gap differently — its decrypted-content event is additionally gated to loopback/mTLS transport by `lib/decrypted-payload-gate.ts` — but still has no *per-viewer* concept once past that gate.

## Dependency hygiene

Given active, ongoing npm supply-chain attacks (compromised popular packages, credential-stealing worms propagating through maintainer accounts) are a real and current threat as of this writing, this repo enforces:

- `ignore-scripts=true` in `.npmrc` — disables all lifecycle scripts (`preinstall`, `postinstall`, etc.) during `npm ci`/`npm install`, reducing the attack surface of compromised dependencies that try to run arbitrary code at install time.
- `save-exact=true` in `.npmrc` — ensures all new dependencies are pinned to exact versions, not broad `^`/`~` ranges.
- Always use `npm ci` (not `npm install`) in any automated/CI context — always installs exactly what the lockfile specifies.
- No new dependency should be added for something you can reasonably build with what's already in the tree, especially anything touching auth, crypto, or credential storage — fewer dependencies is fewer places a supply-chain compromise can hide.
- If you add a dependency and something in your editor/IDE config changes that you didn't make (tasks, extensions, settings files), treat that as a signal to investigate before dismissing it — implanted editor config has been an observed persistence mechanism in real npm worm campaigns.

## Reporting a security issue

This is a personal/hobby project without a formal disclosure program. If you find a real vulnerability (not just something already written down above as a known, documented, intentional gap — e.g. "the app itself has no login", or any of the residual risks listed), open a GitHub issue or reach out directly rather than a public PR with exploit details, so there's time to fix it first.

## If you're extending this project

- Anything you add that increases what's captured, stored, or displayed should be weighed against the fact that this data is sensitive by nature (who you talk to, what sites you visit, what your devices do in the background).
- Before adding any feature that listens on a non-loopback address, stop. Epic #22 closed that gap in one specific, reviewed way: everything LAN-facing goes through Caddy's verified mTLS front door, and the app's own ports stay on loopback. A new listener that doesn't route through Caddy re-opens the gap and gets none of that protection. Route it through the proxy rather than binding it yourself, and re-run `deploy/test-mtls-rejection.sh` after any change to `deploy/Caddyfile`.
- If you add a new dependency, prefer well-audited, widely-used libraries for anything security-critical (TLS, credential storage, auth) over rolling your own — this is standard security engineering practice, not specific to this project, but worth restating given how much of this codebase deliberately avoids it in favor of vetted primitives (the OS Keychain, mkcert-issued certs, a reverse proxy's own TLS implementation) in the parts of the design that do touch security.
