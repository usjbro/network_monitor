# IO Graph Implementation Plan

> **For agentic workers:** execute task by task. Steps use checkbox (`- [ ]`) syntax. Do not implement before James approves this plan. Before editing, create each task's approval gate and worktree (`coordination/scripts/create-gate.sh`, `new-task.sh`). Commit and push only with task authorization. Each task is one PR, and each PR merges before the next starts.

**Goal:** a live IO graph in which several display-filter-defined series show complete per-interval packet and byte counts over a real, pannable and zoomable time axis. Clicking a point shows what the browser actually holds for that interval, and says how much it does not hold.

**Architecture:**
- The capture agent evaluates each series' display filter on every parsed frame, before the 100/s packet-event limiter, using a Rust port of `lib/display-filter.ts`.
- It counts packets and on-wire bytes into 100 ms buckets keyed by frame time, and broadcasts the closed buckets once per tick as `io_buckets`.
- The relay forwards those events and caches the latest `io_series_status`.
- The browser keeps fixed-capacity rings and draws an SVG chart.

**Tech stack:** existing Rust/Tokio/serde and Next.js/TypeScript/React, with Vitest and Playwright. **No new dependency**, Rust or npm (spec D8).

**Spec:** [`2026-11-10-io-graph-design.md`](../specs/2026-11-10-io-graph-design.md). All six decisions were recorded by James on 2026-11-10, including approval of the wire change. Base inspected: `main` at `4f478d8` (the spec squash-merged as #302 on top of `f664407`; no code changed between them). This document is a plan, not implementation evidence.

## Global constraints (from the spec; do not change without James)

- **Off by default, zero cost when off.** With no series configured, the only thing the capture loop does per frame is a relaxed atomic load. No field tree is built, and no state is allocated.
- **Limits:**
  - `MAX_IO_SERIES = 8`, and this cap is provisional (Task 2 benchmark).
  - Series id `^[a-z0-9-]{1,32}$`, unique within a set.
  - Filter source ≤ 2048 characters, with the tokenizer limits 512 tokens, nesting 64, set size 128.
  - `requestId` and `baseEpoch` `^[0-9a-f]{8,32}$`.
  - Bucket width 100 ms, fixed. Grace 500 ms.
  - Closed-but-unsent buckets ≤ 36 000 per series.
  - `lateBuckets` ≤ 256 per series per message.
  - `io_buckets` encoded line ≤ 64 KiB, chunked into several lines, never truncated.
  - Browser rings: 9 000 buckets at 100 ms, 3 600 at 1 s, 1 440 at 1 m. 10 s is derived from 1 s.
  - Rendered points ≤ 2 000 per series.
- **Counts:**
  - Bytes are `original_len`, not `parsed.total_len`.
  - The series field tree is `fields::build_packet_fields(&parsed, &l7_info, link_type, sniff_outcome.status.is_some())` plus `fields::transaction_fields(&txn_event)`, exactly what `build_packet_json` assembles (`main.rs:533-543`).
  - `connection.*` and `*.response_to` are compile errors for a series.
  - Decrypted content is never an input.
- **Time:**
  - Bucket key = `floor(frame_ts_us / 100 000)`.
  - The closing clock is the newest recorded frame time in replay, and wall-clock epoch time live (checked per frame and per tick).
  - A late frame is never placed in a bucket that was already sent.
  - Pause, interface switch, replay error and backlog are `notObserved` ranges, never zeros.
- **Wire:**
  - `io_buckets` and `io_series_status` never pass through `PacketEventLimiter`.
  - Unknown fields and reasons on the TS side never throw.
  - `wire.rs`, `docs/wire-protocol.md`, `lib/types.ts` and `lib/agent-mapping.ts` change together.
- **Bind and invariants:** loopback only, unchanged. Preserve the Webpack/`--webpack` flags. No Caddy changes.

## Corrections found while verifying the spec against source

The plan follows the spec. These points settle details the spec left open, or fix details its own text got wrong. Each is labelled so the reviewer can reject it individually.

1. **Status bootstrap on agent connection (refines D3).** "Sent on every relay (re)connection" is implemented by writing one `io_series_status` line straight to the newly authenticated connection's `write_half`, after `control_auth::write_ack` (`main.rs:3884-3888`) and before the event loop starts. It does not go through the broadcast `tx`, which would wake every subscriber. The relay cache in `lib/stream-response.ts` (spec D3) still covers new browser tabs on an already-connected relay.
   - *Alternative considered:* sending status every tick, as `capture_config` does (`main.rs:3778-3786`). Rejected: it would broadcast up to ~16 KiB of filter source every second for state that rarely changes, and a new tab would still wait up to a second.
2. **Series state crosses threads via a generation counter, not the `CaptureConfigRequest` channel.** Series changes must be compare-and-swapped and acknowledged synchronously in the control task, so the CAS result can be written back. The capture thread only needs to notice "the set changed".
   - So the state lives in `Arc<IoSeriesShared>`, which holds `Mutex<IoSeriesState>` (epoch, revision, compiled set) and `AtomicU64 generation`.
   - The capture thread caches `(generation, Arc<CompiledSet>)` and re-locks only when the generation moves. That keeps the hot path at one atomic load per frame whether series are on or off.
   - *Alternative considered:* routing changes through `CaptureConfigRequest`. Rejected: it is a fire-and-forget queue to the capture thread, so the control task could not return the CAS result.
3. **Closed buckets leave the capture thread through a bounded `std::sync::mpsc::sync_channel`.** The emitter drains it on each tick.
   - Replay uses blocking `send`. That is the spec's "replay reader blocks" backpressure (D4).
   - Live uses `try_send`. A full channel triggers the `backlog` path (D4): the agent stops counting and reports the span and `evaluationSkipped`.
   - Capacity = `MAX_IO_SERIES × 36 000` buckets, counted in entries.
4. **The replay wait is a startup read plus a `Condvar`.** `REPLAY_WAIT_FOR_IO_SERIES` is read once at startup, and only when `REPLAY_FILE` is set. The value `1` enables it; unset or empty disables it; anything else fails startup with a message.
   - The replay reader waits before reading its first frame until the first accepted non-empty set. The control task notifies the `Condvar` on accept.
   - `replayWaiting` is added to `CaptureStatsJson` (`wire.rs:469`) and to `io_series_status`.
5. **`set_io_series` is validated in the control route, not forwarded raw.** The route's existing `set_capture_filter` limit of 1024 characters applies to BPF and stays as it is. The new 2048-character limit applies only to `set_io_series` filter strings.

## Shared types and ownership

Rust (Task 2 owns them, Task 5 widens them):

```rust
pub struct SeriesDef { pub id: String, pub filter: String }               // wire input, validated
pub struct CompiledSeries { pub id: String, pub filter: String, pub compiled: Result<display_filter::Compiled, display_filter::Error> }
pub struct IoSeriesState { pub epoch: String, pub revision: u32, pub series: Arc<Vec<CompiledSeries>>, pub replay_waiting: bool }
pub struct Bucket { pub start_ms: u64, pub packets: u64, pub bytes: u64 }  // Task 5 adds count/sum/min/max
pub enum NotObservedReason { Paused, InterfaceSwitch, ReplayError, Backlog }
```

`display_filter::Compiled::matches(&self, fields: &[fields::Field], frame_len: u32) -> bool` is the only evaluation entry point. `frame_len` is the captured length, so `frame.len` keeps its browser meaning.

TypeScript (`lib/types.ts`, Task 2): `IoSeriesStatus`, `IoSeriesEntry { id, filter, ok, error? }`, `IoBuckets`, `IoSeriesBuckets { id, late, lateBuckets, buckets }`, and `IoBucket = [startMs: number, packets: number, bytes: number]`. Counts above 2^53−1 are not expected at 100 ms granularity. The mapper still parses decimal strings to `bigint`-safe numbers, the same way `field.value` is handled.

- [ ] **Capture-loop integration in `main.rs`:**

Load the generation; if the set is non-empty, build the tree once (correction 2's cached `Arc`), evaluate each `Ok` series, then `observe`. **No tree is built when the set is empty.** Add a `#[cfg(test)]` counter seam on tree construction and assert it stays 0 with no series.
  - **Closing clock (replay): an absolute high-water mark**, `max(frame_ts_epoch_ms)` over the recorded frames seen so far. Buckets therefore close and covered zero-traffic time keeps being published during silence. The granularity is the pcap read timeout; record its actual value in the PR. Replay has no idle path, because its clock only moves with frames and EOF triggers `finalize`.

  - `SourceFrame::Eof` / `ReplayError` (`main.rs:3355-3374`): call `finalize` before `break`.
